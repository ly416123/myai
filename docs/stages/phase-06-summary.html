1. 阶段目标与上一阶段遗留

阶段六为 Agent 配置建立可追溯的版本、离线评测门禁、发布审批、激活/灰度/回滚，以及每个 Run 固定配置快照的生命周期。阶段五已经提供 Worker 输入输出契约，但 Prompt、Skill、模型参数、工具权限和 Worker 契约引用尚未组成统一的不可变发布版本。运行时配置若随静态文件或部署改变，可能导致新 Run 无法确定实际配置来源；运行中恢复也可能难以证明沿用原规则。

2. 本阶段实现

  • 配置内容规范化后生成稳定 SHA-256 Revision；PostgreSQL 保存不可变 Revision、Release、激活指针、门禁尝试、审批记录和追加式发布事件。
  • 发布前关联阶段四离线 Evaluation，由兼容性和显式门禁规则决定是否创建 Release；失败门禁也保留审计尝试。
  • 激活、灰度和回滚通过数据库版本 compare-and-set 更新；按稳定 Run ID 分桶，不支持伪造用户/租户身份的灰度。
  • 新 Run 创建时解析有效 Release 并持久化配置快照；现有 Run 与恢复任务保留原快照。PostgreSQL 另投影 Release ID 和配置哈希便于查询。
  • Runtime、CollaborativeWorkflow 和模型适配器按快照应用提示词、Skill、模型参数、工具 allowlist、Worker 契约引用与预算；工具权限在执行侧再次校验。
  • CLI 提供 Revision/Release、评测门禁、审批、差异、当前版本、历史、Run 快照、激活、灰度及回滚操作。可选自动回滚依据灰度候选 Run 的终态失败率，默认关闭。

3. 阶段六完成时的整体分层架构

实线表示主要调用或数据流，虚线表示由运行记录驱动的可选监控决策。配置生命周期由应用服务控制；模型能力被多个运行层使用，因此作为横向适配能力展示。

图示说明：Revision、Release、门禁尝试与审批事件由配置存储持久化；新 Run 从当前激活指针解析配置后写入自己的快照。运行时通过模型和工具适配器完成执行，RunStore 保存任务及检查点。自动回滚监控默认关闭，开启时读取候选版本的 Run 终态并以 CAS 方式移除候选版本。

4. 关键设计选择

  • PostgreSQL 作为唯一权威配置存储：与 Run、评测现有基础设施一致，利用事务和版本 CAS 保证激活并发安全；没有引入 Redis、MQ 或独立配置平台。
  • 配置不可变，Run 快照固定：避免运行期间漂移，并让恢复任务能按已保存配置继续。替代方案是每次模型调用读取当前配置，会让同一个 Run 在激活切换后行为改变，因此未采用。
  • 先离线评测，再单独审批和激活：保留评测门禁与操作者动作的审计分离。当前审批仅是流程记录，因为没有可信认证身份，不宣称双人审批或生产授权。
  • 灰度键使用稳定 Run ID：当前没有可信用户/租户身份；按身份分桶会产生虚假隔离，因此暂不提供用户级灰度。
  • 自动回滚默认关闭：已实现有限窗口内的运行终态失败率阈值，但它只能检测操作性失败，不能识别回答质量退化；没有语义评测数据时不自动假设质量正常。

  • 拒绝的发布门禁保留审计尝试但不生成 Release；未审批 Release 不能激活、灰度或回滚。
