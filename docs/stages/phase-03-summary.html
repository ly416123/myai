上一阶段遗留问题与本阶段目标

阶段二建立了可运行的单 Agent Workflow，但那一阶段的验收通过只说明当时范围内的状态机、检查点和恢复路径可用，不代表企业级运行架构已完成。进入阶段三前后确认的遗留工程缺口如下：

阶段二遗留问题对阶段三的影响本阶段处理结果
RunStore 只有内存与本地 JSON 文件实现，单文件原子替换不提供多进程锁、事务、租约或集群可用性。并发 Worker 只能在一个 JVM 内调度；多个实例恢复/写同一个父 Run 仍可能竞争。遵守阶段三当时明确的本地存储和单实例范围，将父 Run 与子任务放在同一记录；跨进程协调仍是企业化改造项。
阶段二只有单 Agent 循环，没有 Supervisor 规划、静态 Worker、依赖调度和子任务级记录。无法按角色拆分任务，也无法跟踪父任务与多个执行步骤的关系。新增 Supervisor–Worker Workflow、Worker allowlist、依赖/并发调度、父 Run 子任务和 Worker 关联步骤。
RunRecord 没有持久化 Workflow 类型，两个恢复入口无法判断检查点属于单 Agent 还是协作流程。错误入口可能改变恢复执行路径，协作检查点还可能重新规划并重复模型调用。本阶段验收时发现并修复：增加 RunType，两个入口在任何检查点修改之前拒绝类型不匹配；双向回归已通过。旧 JSON 无类型字段时按单 Agent 兼容读取。
阶段二日志和评测以本地记录、Fake ModelClient 固定样例为主，没有企业级指标/告警，也没有真实模型质量基线。不能据此判断 Supervisor 计划质量、线上时延、费用或多 Agent 的真实收益。补充父子步骤本地记录和确定性单 Agent/多 Agent 对照；真实模型评测与外部监控仍未完成。
任意工具超时或进程中断都不能证明外部副作用已撤销；缺少工具端幂等或事务协议时无法保证 exactly-once。Worker 并发会扩大副作用不确定性，不能自动重放不确定工具。沿用 PENDING/IN_PROGRESS/INDETERMINATE 边界，未知结果不自动重放；企业业务工具仍需定义幂等键、补偿或人工核对协议。

本阶段目标是在现有单 Agent Runtime 上增加受约束的 Supervisor–Worker 协作，并用确定性样例比较结果和调用开销。阶段三原始范围明确要求暂不引入数据库、消息队列、跨进程协调和外部监控，因此本阶段保留 JSON Store；这是阶段范围选择，不是项目定位或未来企业架构的限制。

当前项目定位：MyAi 按企业级 Agent Runtime 建设。阶段三验收通过不等同于生产就绪；下一阶段应单独完成部署、持久化、并发一致性、密钥、安全、监控、容量和恢复策略的架构评审与落地计划。

实现与设计决策

需求实现选择理由
显式路由和任务计划CollaborativeWorkflow 通过一次结构化规划选择 NO_SPLIT 或 DELEGATE。非法 JSON、未知 Worker、空/超量任务、重复 ID/规范键、无效依赖、环和交付项映射错误均在 Worker 启动前作为受控失败。复用一次 Supervisor 规划调用完成路由，不增加分类模型调用；非法计划不降级执行，避免跳过计划校验。
计划去重与交付校验判重键由 workerId、Unicode NFC、去首尾空白并折叠连续空白的描述、排序后的依赖集合组成；描述保留大小写。使用结构化值比较，避免分隔符字符导致误碰撞。计划列出交付项和任务映射，汇总前按成功任务结果核对覆盖。精确落实需求定义；覆盖验证不再调用模型。
Worker 边界静态 WorkerRegistry 注册计算、时间、天气 Worker；每个 Worker 有职责、指令、工具 allowlist、单任务模型和工具预算。工具注册表按 allowlist 受限。模型只能选择已注册角色；不把全部工具权限或所有 Worker 对话共享给每个 Worker。
并发、依赖与预算固定大小线程池并受 maxParallelism 限制；独立任务可同时运行，依赖任务等上游成功。Supervisor、Worker、重试和汇总共享父 Run 的原子模型/工具预算与 Deadline。不引入分布式调度，也不以虚拟线程绕开并发预算。
父子记录与恢复RunRecord 增加计划、子任务、Worker 消息、关联字段及持久化 RunType；RunStep 增加 taskId、workerId、phase。两个恢复入口分别要求 SINGLE_AGENT 或 COLLABORATIVE，先校验类型再设置恢复标记和保存。PENDING 工具可恢复；IN_PROGRESS 工具记为 INDETERMINATE 并回传未知结果，不重放。沿用阶段二 RunStore 和单父 Run 生命周期；旧 JSON 缺少 RunType 时默认按单 Agent 读取，旧 RunStep 构造形式仍兼容。
部分失败和记忆边界成功任务结果可汇总；失败或被跳过的任务不能伪装成成功。缺失交付项会出现在输出中，部分可用结果为 PARTIAL，无成功结果为 FAILED。Worker 输入包含父请求、任务和显式依赖结果。共享只发生在一次父 Run 内，且按依赖声明传递；没有加入跨 Run 长期记忆。
用户入口默认文本仍走单 Agent；新增 /multi <任务> 和 /multi-resume <runId>。/runs 展示父 Run 的状态和调用摘要。以 opt-in 方式展示额外规划/汇总成本，保留现有 CLI 使用习惯。

主要替代方案

  • 未采用独立分类模型，因为规划调用可同时决定路由并生成任务，调用更少。
  • 未创建子 Run，因为阶段二 RunStore 已可持久化父记录，单父记录更便于阶段三统一预算、取消和恢复。
  • 未引入外部队列或数据库是阶段三提示词的显式范围约束；这不代表该方案适合作为多实例企业生产存储。
  • 未增加 Supervisor 二次质量复核；本阶段按需求使用确定性的交付项覆盖检查。

评测与可观察结果

  • 覆盖 NO_SPLIT 同父 Run 回退、DELEGATE 分派、非法 JSON/无效计划拒绝、任务数量上限、Worker allowlist、每 Worker 模型与工具预算和父级总预算。
  • 验证独立任务并发上限、依赖顺序、只注入声明的依赖结果、部分失败/跳过、缺失交付项以及无成功结果时失败。
  • 验证 Deadline、取消、JSON 文件跨 Store 实例恢复、PENDING 工具只执行一次，以及 IN_PROGRESS 工具不重放。
  • 双向交叉恢复测试验证单 Agent Runtime 拒绝协作 Run、CollaborativeWorkflow 拒绝单 Agent Run；拒绝前不改变检查点，且不会请求模型或重新规划。旧 JSON 缺少 RunType 时仍按单 Agent 读取。
  • 在同一确定性“6 × 7”任务上，单 Agent 和协作流程均返回 42；样例中单 Agent 使用 2 次模型调用，协作流程使用 4 次（规划、Worker 两轮、汇总）。这显示该任务上协作流程有额外调用开销。
  • 新增规范化判重边界测试，确认 NFC 与空白归一化生效、大小写保留，且结构化依赖集合避免分隔符误碰撞。

Fake 测试的耗时只用于断言字段、Deadline 和调度行为；并发测试验证任务确实重叠，但没有作为真实性能提升证据。没有执行真实模型质量、实际费用或线上延迟比较。

已知限制与下一步

  • 取消或超时只能中断等待线程，不能撤销已发生或仍在运行的外部副作用；没有工具端幂等键或事务协议时，不保证 exactly-once。
  • 模型请求在进程崩溃后可能重发并产生重复费用；多进程同时恢复同一个 Run 的锁/租约不在本阶段范围。
  • l5 环境（ly@192.168.122.55）确认运行单节点 K3s v1.36.4+k3s1；2026-11-12 快照为 4 CPU、7.2 GiB 内存、根卷可用约 87 GiB，Docker/Compose 命令不可用。非系统工作负载停用后 available 内存约 5.5 GiB（此前约 1.0 GiB）。29 个 Deployment 已缩至 0（此前 20 个副本数非零）、4 个 StatefulSet 已缩至 0、2 个 CronJob 已暂停；所有非系统 Pod 已停止，K3s 和 kube-system 保持运行，数据 PVC 保留。停机前状态记录在 l5 的两个 /tmp/l5-*-before-shutdown-2026-11-12.txt 文件中。资源会变化，部署前需复核并评估是否适合共置数据库或 MQ。
  • 检查点保存父请求、模型消息、工具参数和结果；应限制本地运行目录访问，避免把密钥或凭据写入任务/工具数据。
  • 固定 Fake 样例只证明已测试的控制流，不证明真实模型规划/工具选择质量、生产安全性或真实性能。
  • 没有跨 Run 长期记忆。未来如需加入，需先定义保留与过期、纠错机制、数据访问控制和敏感信息删除策略。
