# Agent 记忆能力候选规划

> **文档状态：** 阶段七已在本机完成首版验收；本文记录阶段七之后的候选演进方向，不代表这些后续能力已经排期或实现。阶段七远端 CI 与 L5 部署状态见[阶段七总结](../stages/phase-07-summary.html)。

## 1. 目标与当前现状

MyAi 既保存 Run 的消息历史、执行步骤和检查点，也已在阶段七增加跨 Run 的显式结构化偏好/事实记忆。Run 状态是任务运行记录；MemoryStore 保存跨 Run 可检索的条目，Run 创建时将命中项固定为快照。阶段七首版只面向单一受控 CLI namespace，不含可信用户/团队身份、自动提取或语义检索。

本规划描述阶段七首版之后可能增加的能力：让 Agent 在明确的数据边界、授权和保留规则下，进一步提取、保存、检索、修正与遗忘可复用的信息。记忆应服务明确的业务场景，不以“保存更多对话”为目标。

## 2. 记忆范围术语

| 范围 | 含义 | 当前状态 | 建议处理 |
| --- | --- | --- | --- |
| 短期记忆 | 当前 Run 的对话和工作上下文 | 已由消息历史与检查点提供 | 继续归 Runtime 管理；需要时单独评估上下文裁剪和摘要，不重复建设存储 |
| 中期记忆 | 当前 Workflow 或一组关联 Run 的阶段结果、决策和引用 | 有父子任务结果与持久化状态，但没有通用记忆抽象 | 先用结构化交付物和引用；明确跨 Run 复用场景后再扩展 |
| 长期记忆 | 跨 Run 保留并按需检索的偏好、稳定事实或经确认的经验 | 阶段七已交付单 namespace、显式管理、确定性词面检索和 Run 快照；待远端 CI 与 L5 验证 | 下一步先通过固定评测验证误记、漏召回、冲突和回答收益，再决定是否扩展提取或检索能力 |

“短期/中期/长期”描述的是作用范围和生命周期，不预设必须使用三套数据库或三种技术。Run 检查点不能直接当作长期记忆查询源。

## 3. 候选业务场景

实现前必须选定一个可验证场景，建议优先从以下低风险场景中选一个：

1. **用户偏好：** 例如回答语言、输出格式或用户明确要求记住的偏好。
2. **项目事实：** 例如某个项目经用户确认的约束、术语或固定决策。
3. **任务经验：** 某类任务经人工确认后可复用的结果或操作注意事项。

第一版不自动把所有对话写入长期记忆，不把模型推断出的个人属性作为事实保存，也不把工具执行原文和完整 Run 历史搬入记忆库。

## 4. 候选架构边界

- **MemoryService：** 面向 Runtime/Workflow 提供受控的记忆查询、提议写入、确认、更新和删除接口。
- **MemoryStore：** 持久化记忆条目及其来源、版本、状态和生命周期元数据；存储实现由接口隔离。
- **MemoryPolicy：** 按可信调用上下文、项目范围和记忆类型判断是否可读写。当前 `local-cli` 标识未认证，不能据此实现用户隔离或用户级记忆。
- **Memory Retriever：** 依据当前任务检索少量相关条目；只将选中的内容注入本次模型请求，不把整个记忆库塞入上下文。
- **来源与审计：** 记忆条目应能追溯来源 Run/步骤或显式用户确认；记录操作类型和时间，但避免在日志中复制记忆正文或敏感值。

候选数据字段：`memoryId`、作用域、类型、正文或结构化值、来源引用、创建/更新时间、确认状态、有效期/过期策略、版本、状态（有效/待确认/已撤销）。具体字段须由选定场景确定，不要求所有类型共用一个大而全的结构。

## 5. 生命周期与行为规则

1. **提取：** Runtime 可提出候选记忆，但写入是否需要用户确认应由记忆类型和业务策略决定；第一版默认显式确认后写入。
2. **读取：** 每次任务按当前可信作用域和相关性取有限数量的条目；未命中时按无记忆继续，不推测或编造。
3. **更新与冲突：** 新信息不得静默覆盖旧值；保留版本或明确冲突状态，并提供确定的更新/撤销流程。
4. **纠错与删除：** 支持按稳定 ID 查看、修正、撤销或删除记忆，并使后续检索不再返回已撤销条目。
5. **过期：** 不默认永久保存。每类记忆需声明保留方式；法规、合同和业务保留期限未确认前，不启用自动清理，也不宣称满足删除合规。
6. **上下文控制：** 注入内容应有条数或 token 预算，记录命中数量和来源引用，不将整个记忆正文写入普通运行日志/Trace。
7. **故障处理：** 记忆读取失败时由策略明确选择拒绝任务或降级为无记忆运行；写入失败不得伪报成功，且不得影响已完成的业务副作用。

## 6. 存储与检索的演进选择

建议从 PostgreSQL 结构化存储开始，按精确作用域、类型和状态筛选，再用简单文本检索或受控排序找候选。该方式可复用现有企业存储运维，也便于审计和确定性测试。

只有当选定场景的检索质量经固定样例证明无法满足需求，且数据规模与运维收益明确时，才评估全文搜索或向量检索。引入向量能力前需要比较 PostgreSQL 扩展与独立向量服务的维护成本、备份/恢复边界、数据驻留和删除语义；不因“Agent 记忆”这一名称默认引入向量数据库。

## 7. 建议分期

### 设计与试验

- 明确首个业务场景、作用域、可信身份来源、可保存内容和明确禁止保存的内容。
- 建立小型固定数据集，验证提取、检索、冲突、纠错、撤销和过期规则。
- 使用 Fake Runtime/Store 覆盖行为，不调用真实模型或真实密钥。

### 最小可交付版本

- 实现结构化 MemoryStore、受控查询与显式写入/确认。
- 在一个选定入口接入读取，并限制上下文注入预算。
- 提供列出、查看、修正、撤销/删除的受控 CLI 操作。
- 记录脱敏运行事件和来源引用，提供确定性回归评测。

### 后续候选

- 多作用域隔离、自动候选记忆、跨任务经验归纳、全文/向量混合检索及自动过期清理。
- 只有身份、授权、数据分类和保留政策落实后，才考虑生产用户级长期记忆和自动写入。

以上分期是建议，不能替代阶段六完成后的需求确认和资源评估。

## 8. 验收建议

- 固定样例验证作用域隔离、读取排序/上限、写入确认、版本冲突、纠错、撤销和来源追踪。
- 证明无可信身份时不会将未认证的 `local-cli` 当作用户或租户边界。
- 证明模型未命中记忆时不会伪造记忆；记忆存储故障行为符合配置策略。
- 证明敏感内容不会进入常规日志/Trace，未确认的候选不会被当作已确认事实注入。
- 验证上下文预算与记忆条数限制；报告固定评测的成功、失败、调用数和耗时，不把小样例结果描述成整体 Agent 质量保证。
- 若实现自动删除，另行验证删除范围、失败重试和审计记录，并先确认业务保留策略。

## 9. 明确不在本候选范围

- 阶段六的配置版本、发布、灰度和回滚功能。
- Multi-Agent 或 Worker 编排重构。
- 默认永久保留所有对话、完整 Run 检查点或工具参数。
- 未经确认自动推断并保存敏感个人属性。
- 在身份和授权未明确时提供用户/租户隔离承诺。
- 仅因增加记忆而引入 Langfuse、独立向量数据库或其他外部平台。
