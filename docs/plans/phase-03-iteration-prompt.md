## 阶段选择说明

项目已完成阶段二：单 Agent Workflow 具备本地检查点、恢复、预算、运行记录和确定性回归评测。按阶段路线进入 Multi-Agent；本阶段验证多 Agent 对明确可分工任务的作用，不扩展成 Agent Platform。其单机架构限制是阶段三的范围选择，不代表企业架构目标。

本阶段以**最小 Supervisor–Worker 协作为主线，并与现有单 Agent 基线比较**。只对彼此独立的子任务尝试受限并行；任务有依赖时按顺序执行。当前项目的本地 JSON 存储和单实例定位继续保留，不在本阶段解决多进程运行协调。

以下策略已经确定，实施时不再作为待确认项：

- 子任务部分失败时，允许汇总已完成结果，但必须指出失败任务和缺失信息；依赖失败的下游任务应跳过。
- 计划明确表示无需拆分时，直接回退至原单 Agent 流程；非法 JSON、未知 Worker、依赖环等计划错误作为受控失败，不将未经校验的计划交给单 Agent 执行。
- 子任务和 Worker 步骤由父 `RunRecord` 保存，使用稳定的任务/Worker 关联 ID；优先扩展现有数据模型并保持旧 JSON 检查点可读，不新增独立子 Run 生命周期。
- 每项计划任务必须有非空且唯一的 `taskId`；同时按“workerId + Unicode NFC 规范化、去首尾空格并折叠连续空白后的任务描述 + 排序后的依赖 taskId 集合”生成判重键。重复 taskId 或判重键冲突均在执行前作为无效计划拒绝；任务描述不做大小写折叠，以免改变代码标识符语义。
- 本阶段的“覆盖原始目标验证”只做确定性结构校验：计划显式列出预期交付项，并映射到一个或多个任务；所有依赖都必须有效，汇总前核对每个预期交付项是否有成功任务结果。不增加 Supervisor 模型复核调用。
- 若部分任务失败但仍有可用结果，父 Run 以 `PARTIAL` 终态返回部分汇总并列出失败和缺失项；没有可用结果、计划无效或系统级执行错误则为 `FAILED`。如需扩展 `RunStatus`，须保持旧检查点兼容并补充状态迁移测试。
- Fake 评测只验证调度顺序、状态和耗时字段是否记录；不据此宣称真实并行提速。真实延迟比较如未执行，只能列为未验证。

本阶段其他横切能力按以下优先级纳入：

- **P0：评测与正确性验收。** 必须有确定性回归，验证单 Agent 回退、多 Agent 规划/调度、失败、预算、恢复等行为。
- **P1：意图路由与父子可观测性。** 由 Supervisor 的一次结构化规划给出 `NO_SPLIT` 或 `DELEGATE`；不另建分类模型。扩展父 Run 的本地记录，能追踪 task/worker 关联、状态、耗时、失败和 Token 用量。
- **P2：记忆治理边界。** 明确父任务、Worker 输入、Worker 输出摘要之间共享什么、不共享什么，并按 Worker 限制上下文和工具访问。本阶段不做跨 Run 长期记忆、向量检索或记忆存储服务。

执行时无需再次向用户确认以上策略。若源码证据表明某项与现有状态模型或恢复语义冲突，应说明冲突和最小调整方案后继续；不得静默改变已确认的产品行为。

- `AgentRuntime` 已支持模型/工具循环、`runId`、运行状态、检查点、恢复、取消、模型与工具预算、Deadline 和日志记录。

### 阶段目标

实现一个可解释、可测试的 Supervisor–Worker 模式：Supervisor 在结构化规划中同时判断任务应直接走单 Agent（`NO_SPLIT`）还是拆分委派（`DELEGATE`），并在后者情况下生成受约束的子任务计划；Worker 使用限定职责、上下文和工具完成子任务；汇总前执行确定性的计划/交付项覆盖校验，不增加模型复核调用。通过同一组确定性任务比较单 Agent 与多 Agent 的结果及调用开销，说明适用边界。Fake 测试只验证耗时记录和调度顺序，不证明真实性能提升。

### 阶段优先级

- **P0：** 正确性与固定回归评测，是本阶段验收门槛。
- **P1：** Supervisor 的最小意图路由，以及父 Run 中的父子任务可观测记录。
- **P2：** Worker 上下文访问与信息共享治理；只制定并落实单次父 Run 内的隔离/共享边界，不增加长期记忆系统。

### 功能要求

1. **先定义 Agent 与 Worker 的边界**
   - 基于当前 `AgentRuntime` 的职责设计最小可复用抽象，例如 Agent 配置、Worker 注册表、Agent 执行器或协作 Workflow；由你根据代码结构选择，不要机械照搬命名。
   - Worker 必须静态注册且具有明确名称、职责说明、可用工具范围和执行预算。模型只能从已注册 Worker 中选择，不得动态创建任意 Agent 或工具。
   - 每个 Worker 的模型指令、工具可见范围和结果格式要清晰；不要把整个工具注册表无差别暴露给所有 Worker。

2. **结构化任务拆分与校验**
   - Supervisor 产出的计划应使用明确结构（例如 JSON DTO），并在执行前校验 Worker 名称、任务内容、任务数量上限及依赖关系。
   - 每个计划项必须带非空、唯一的稳定 `taskId`。此外，以 `workerId`、规范化任务描述和排序后的依赖集合构成规范化判重键；相同判重键代表重复任务。描述规范化采用 Unicode NFC、去除首尾空白、折叠连续空白，不做大小写折叠。
   - 非法 JSON、未知 Worker、空任务、重复 taskId、重复判重键或超过预算时，应产生受控失败，不得执行未校验的子任务。
   - 使用 Supervisor 规划结果完成最小意图路由：经过结构校验的 `NO_SPLIT` 结果直接回退到现有单 Agent 路径；`DELEGATE` 携带经过校验的任务列表。
   - 非法 JSON、未知 Worker、空任务、重复任务、超任务数、依赖环或其他计划校验失败均作为受控失败；不得把无效计划回退后交给单 Agent 执行。
   - 不增加独立意图分类模型或额外分类调用；如源码与模型协议限制使该设计无法实现，先说明证据，再采用调用数更少且行为等价的最小方案。

3. **依赖感知的执行与受限并行**
   - 对确认互相独立的子任务可以并行；存在依赖关系的任务按拓扑顺序执行。
   - 设置并发上限，保证异常、超时、取消和 Deadline 能收敛到可解释的父任务结果。
   - 不要把“使用虚拟线程”当成并发无限制的理由；并行度必须受配置预算控制。
   - 多 Agent 的执行与汇总必须受同一个父 Run 的总模型调用数、工具调用数和 Deadline 约束，不能让每个 Worker 各自重置预算后绕过上限。

4. **结果汇总与失败策略**
   - 汇总阶段只能使用父任务和 Worker 的实际返回结果，不得把失败的子任务伪装成成功。
   - 部分失败时允许汇总已成功子任务，并明确列出失败任务及缺失内容；若某任务依赖失败，则跳过它及其受影响的下游任务。
   - 本阶段覆盖验证采用确定性结构校验：计划必须声明预期交付项并映射到任务；检查依赖有效，汇总前检查每个预期交付项是否至少有一个成功任务结果。不增加额外 Supervisor 模型复核调用。
   - 若部分任务失败但仍有可用结果，保存并返回部分汇总，列出失败任务和缺失交付项，父 Run 使用终态 `PARTIAL`；若没有可用结果、计划无效或系统级错误，父 Run 使用 `FAILED`。如需扩展 `RunStatus`，保持旧 JSON 检查点可读并测试状态转换。
   - 定义全成功、部分失败、超时、取消和覆盖校验失败时的行为；能安全继续的场景允许部分结果，但必须向调用方说明缺失内容。
   - 若 Worker 使用会产生外部副作用的工具，遵循阶段二的 PENDING/IN_PROGRESS/INDETERMINATE 语义，禁止不安全的自动重放。当前演示若没有合适的副作用工具，不要为了测试随意添加真实副作用。

5. **父子执行的记录与可恢复性**
   - 在现有可观测记录中能够区分父 Run、Supervisor、Worker、子任务和汇总步骤；记录稳定关联 ID、状态、耗时、错误类别及可获取的 Token 用量。
   - 子任务与 Worker 步骤保存在父 `RunRecord` 中，不创建独立子 Run 生命周期；使用稳定 taskId/workerId 或等价关联字段。
   - 先审查阶段二 RunStore 是否能安全表达子任务检查点。若要扩展数据模型，应保持旧 JSON RunRecord 可读或提供明确迁移；不要引入未说明的数据格式破坏。
   - 明确进程中断时父子步骤如何恢复。只恢复已验证且安全的待执行步骤；未知副作用不能自动重放。

6. **单次 Run 内的记忆与上下文治理**
   - 明确区分父任务原始输入、Supervisor 规划、Worker 专属输入、Worker 结果摘要和最终汇总；避免把所有 Worker 的完整上下文无差别广播给其他 Worker。
   - Worker 只接收完成其子任务所需的父任务信息、明确列出的依赖结果和自身职责提示；工具权限仍使用 allowlist。
   - 记录/Checkpoint 遵循现有敏感数据告知与日志脱敏规则；不要把 API Key 或凭据放入共享上下文。
   - 本阶段不实现跨 Run 记忆、用户画像、向量检索、摘要压缩服务或长期记忆生命周期管理；在文档中说明未来扩展需要回答的数据保留、过期、纠错和访问控制问题。

7. **与现有单 Agent 的比较评测（P0）**
   - 设计一组小而确定的任务，由 Fake ModelClient 和确定性工具驱动，不访问真实模型 API、不读取真实密钥。
   - 对相同任务分别运行单 Agent 基线和 Supervisor–Worker 流程，检查最终结果、任务分派、工具范围、模型/工具调用数、总耗时字段和失败行为。
   - Fake 测试中的耗时仅用于确认测量字段和先后/并发调度行为，不得作为真实性能提升证据；真实模型或真实环境的性能比较若未实际执行，应清楚标为未验证。
   - 评测需覆盖：成功拆分、无需拆分/回退、非法计划、未知 Worker、重复 taskId、规范化判重冲突、交付项缺失、独立任务并行、依赖任务顺序执行、子任务失败与 `PARTIAL` 终态、无可用结果时的失败、总预算耗尽、Deadline/取消及恢复边界。
   - 不要把固定 Fake 样例宣称为真实模型质量证明。可提供可选手动演示，但不得让自动化构建调用真实模型或产生 API 费用。

8. **用户入口与文档**
   - 保持现有默认单 Agent CLI 行为不变。为多 Agent 演示增加明确的 opt-in 入口（例如独立命令或命令前缀），由你选择最小且清楚的交互方式。
   - 更新 README，说明两种模式的差别、适用条件、预算与恢复语义、如何运行固定评测，以及多 Agent 的额外调用成本和失败面。
   - 更新阶段文档索引。验收通过后新增 `docs/stages/phase-03-summary.html`；该总结必须记录真实实施和验收结果，不要预先写成通过。

## 本阶段明确不做

- 不默认把所有任务升级为 Multi-Agent；无清晰分工时应回退到单 Agent。
- 不为“看起来并行”而拆成多个 Worker；要由任务依赖和职责边界决定。
- 不上来就建设通用平台、分布式调度或外部监控。
- 不把 Fake ModelClient 的回归结果当成模型回答质量证明。
